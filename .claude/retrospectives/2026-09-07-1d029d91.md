### 1. Fix the inverted `--is-ancestor` direction in CLAUDE.md §8

- **type**: `claude-md`
- **target path**: `.claude/CLAUDE.md` §8 (the `Worktree-isolált commit
  visszavezetése a branch-re` bullet, replace the
  `Az ancestry check:` paragraph and the trailing "helyes parancs" line)
- **rationale**: The current text teaches the wrong direction. It says
  `--is-ancestor <SHA> <branch>` exits 0 "if SHA is the branch's
  descendant" and translates `--is-ancestor A B` as "is B an ancestor of
  A" -- both backwards from the actual semantics (`--is-ancestor A B`
  exits 0 iff A is the OLDER commit, i.e. A is an ancestor of B). To
  verify "SHA is a descendant of branch", the correct invocation is
  `--is-ancestor <branch> <SHA>` (older first). The session verified
  this directly with two probes (see Evidence) AND the same trap fired
  in the ca9d811f corpus precedent. Non-obvious, recurring, broadly
  reusable for every cycle that does worktree -> branch fast-forward
  merges, which is the dominant refactor-cycle pattern.
- **full proposed content** (replace the sentence pair inside the
  `Worktree-isolált commit visszavezetése a branch-re` bullet):

```markdown
Az ancestry check: `git merge-base --is-ancestor <branch> <SHA>`
exit 0-val ha a SHA a branch DESCENDANTJE (1-gyel ha nem); a
flag argumentum-sorrendje az "older first": `--is-ancestor A B`
kérdezi "A ancestorja-e B-nek", exit 0 ha A az idősebb. Tehát
"SHA a branch-en van-e (még nincs mergelve)" ellenőrzésére a
```

### 2. Memory entry: scope expansion via production-caller check (NOT catch-site check)

- **type**: `memory`
- **target path**: `.claude/shared-memory/` (topic file + MEMORY.md index
  line)
- **rationale**: When migrating a `} catch { return <fallback> }` to a
  typed `throw`, the plan-step `grep` framed as a "catch site" check
  actually returns ALL callers, not just catch sites. If any caller has
  no try/catch around the call, the throw becomes uncaught on the rare
  error path that the silent catch had previously hidden -- which can
  manifest as HTTP 500s or process crashes. The A.8 cycle hit this
  directly (2 callers in `src/memory.ts:83` and
  `src/web/routes/memories.ts:89` had no try/catch around `searchMemories`).
  The session surfaced the conflict in planning, got user approval for
  the scope expansion (3 extra files, ~25 lines for try/catch wrappers
  with `instanceof MemoryStoreError` narrowing), and the throw migration
  landed cleanly. This is the canonical example for any future
  silent-catch -> typed-throw migration in this codebase. Non-obvious
  (the grep frame as "catch site" vs. caller list is easy to miss),
  broadly reusable, cost a planning cycle to work out.
- **full proposed content**:

  - **topic name**: `silent-catch-to-typed-throw-scope-check`
  - **index one-line summary**:
    `When migrating "} catch { return fallback }" to typed throw, treat grep output as CALLER list not CATCH list; callers without try/catch need a wrapper added in the same cycle`
  - **body**:
    ```
    Cycle owner: session 1d029d91 (2026-09-07), A.8a + A.8b
    (commits 2c4669f and 283fd82 on refactor/classbase).

    Pattern: when a refactor migrates a `} catch (e) { return <X> }`
    fallback to a typed `throw new XxxError(...)`, the planning grep
    framed as "find catch sites" actually returns the full CALLER list
    (callers + their catch sites). Two outcomes:

    1. Caller has its own try/catch wrapping the call -> the throw is
       compatible with the existing error-handling layer, scope
       unchanged, throw migration is local.
    2. Caller relies on the silent fallback (no try/catch around the
       call) -> the throw becomes uncaught, breaks the rare-error path
       that the silent catch had previously hidden. Two responses:
       (a) add a try/catch wrapper in the caller that narrows on
           `instanceof XxxError` and falls back gracefully (scope
           expansion); OR
       (b) keep the silent catch in this caller (no-op, but defeats
           the goal).

    In A.8 the 2 production callers
    (`src/memory.ts:83` -> `buildMemoryContext`,
    `src/web/routes/memories.ts:89` -> `/api/memories` handler) had no
    try/catch around `searchMemories`. Option (a) was chosen -- 3 extra
    files, ~25 lines added in the same cycle, user-approved. Outcome:
    throw migration landed cleanly with graceful degradation (empty
    FTS results / LIKE fallback) instead of uncaught errors.

    Adversarial prompt when planning a throw migration: for each entry
    in `grep -rn '<func>' src/ --include='*.ts' | grep -v __tests__
    | grep -v '<file>'`, classify it as "has own try/catch" or
    "relies on fallback". The "relies on fallback" entries are the
    scope-expansion candidates.

    Refs: src/memory.ts:84-94, src/web/routes/memories.ts:89-99,
    CLAUDE.md §7 "kötelező mindig commitolni" (the scope expansion
    landed in 2 commits, no orphan changes).
    ```
