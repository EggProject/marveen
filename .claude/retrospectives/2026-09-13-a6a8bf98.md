## Proposals

### 1. Shared-memory entry for "vitest uses istanbul provider, not c8"

**type**: memory
**target path**: `.claude/shared-memory/vitest-istanbul-ignore-syntax.md`
**rationale**: Trap that cost ~4 vitest re-runs to diagnose in this
session. The vitest config (`vitest.config.ts:33`) sets
`provider: 'istanbul'`, so the `/* c8 ignore next */` comment syntax
is silently inert — coverage stays at the same percentage with no
warning. The correct syntax is `/* istanbul ignore next */`. Single
corpus hit, but the file lives at one fixed path, so the trap is
deterministic for the lifetime of the config and any future cycle
that adds unreachable branches will hit it. The trap is also
non-obvious (c8 is the de facto standard for V8 coverage; istanbul
is the older IstanbulJS form that `@vitest/coverage-istanbul` uses).
Shared-memory is the right home per the routing rule ("a trap that
already cost time → shared-memory"); CLAUDE.md is too high-prominence
for a config-specific fact.

Proposed topic file content:

```
# vitest uses istanbul provider — ignore-comment syntax is `/* istanbul ignore next */`

The repo's `vitest.config.ts` (provider: 'istanbul', line 33) uses
`@vitest/coverage-istanbul`, NOT c8. Therefore the `/* c8 ignore next */`
comment is silently inert — coverage stays unchanged across runs, no
warning. The correct syntax is `/* istanbul ignore next */`. Switching
between the two brought coverage from 89.65% to 100% in a single vitest
run in the G.2 cycle (commit `fda697d`).

Trap: when adding unreachable branches and trying to suppress them,
the default instinct is `c8` (because c8 is the V8-coverage de facto
standard). Always check `vitest.config.ts` `provider` first. If
`istanbul`, use `/* istanbul ignore next */`.

Precedent: 2026-09-13 a6a8bf98 (G.2 IngestWorker extraction); the
in-session retrospective `.claude/retrospectives/2026-09-12-g2-ingest-worker.md`
documents the full diagnostic sequence.
```

Index one-liner: `vitest istanbul provider: ignore-comment is \`/* istanbul ignore next */\`, NOT c8`

Proposed addition (insert as a new bullet after the existing
"`/code-review` skill `disable-model-invocation` flag-gyel
rendelkezik..." bullet in §8):

```
- **`/code-review max --fix` external-API failure fallback.** A plan
  that ends with `/code-review max --fix` must include BOTH a
  user-unavailable fallback AND an API-down fallback. The
  user-unavailable case (user away / declines) is documented in the
  existing rule; the API-down case (HTTP 429 rate limit, DNS
  ENOTFOUND, host unreachable) is NOT. On API failure: capture the

  re-invoke. A plan that only handles the user-unavailable case will
  silently land code without review on the first API blip.
```
