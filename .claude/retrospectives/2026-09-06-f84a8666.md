### 1. Codify the "never skip bug findings" rule in CLAUDE.md §8

- **type**: `claude-md`
- **target path**: `.claude/CLAUDE.md` §8 (new bullet, after the
  existing "Coverage szám dokumentációba csak `MARVEEN_TEST_*` flag
  NÉLKÜLI futásból kerülhet." bullet, before the next bullet)
- **rationale**: The `/code-review max --fix` skill puts findings
  in a `Skipped` section when their fix scope exceeds what `--fix`
  can auto-apply, or when they touch code outside the diff range.
  The agent in this session used this skip path for TWO confirmed,
  reproducible bugs (DB.ts migration FD leak + migrateTaskRunsFromJson
  race) and the user rejected the skip with three sequential messages,
  ending with the absolute negative form "nincs ilyen hogy release
  elott javitjuk mert el lesz felejtve". The skip-rationale from
  Honcho memory shows the agent understood these were real bugs --
  it just deferred them. The user has now stated the standing rule
  explicitly: a known bug finding from code-review must be EITHER
  fixed in the same session OR written to memory (Honcho
  `create_conclusion`) immediately, with the path "fix before
  release" forbidden because such items get forgotten. This needs
  to be in CLAUDE.md so the next `/code-review max --fix` invocation
  doesn't re-derive the lesson. Precedens: this session
  (3 user corrections) + the existence of two now-correctly-fixed
  bugs that should never have been skipped in the first place.
- **full proposed content** (new bullet):


## Not proposed

- **Add a checklist to `/code-review max --fix` to make the Skipped
  path explicit.** Considered because the bug pattern was "agent
  auto-applied some findings but skipped others", and a checklist
  would surface the skips. Rejected: the skill is user-invoked with
  `disable-model-invocation` per CLAUDE.md §8, so the skill itself
  cannot be modified from here, and the standing rule belongs in
  CLAUDE.md, not in the skill's internal logic. The agent sees the
  skill output and must handle it; the rule goes in §8.
- **Rule that ALL code-review findings must be fixed in the same
  session.** Rejected as too broad: trivial findings (style,
  naming, comments) and design-level findings (architecture
  changes, large refactors) are legitimately deferrable. The user's
  correction was scoped to BUGS ("ha tudunk bugrol"), not findings
  in general. The proposal is scoped to bug findings only.
- **Rule that the agent must open a sub-worktree proactively during
  the original /code-review run for any finding it might want to
  skip.** Rejected as over-engineered: the rule "fix OR write to
  memory" already covers it, and forcing a sub-worktree for every
  potential skip would create noise. The trigger is the user's
  explicit veto, not a pre-emptive worktree creation.
