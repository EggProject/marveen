### 1. Add CLAUDE.md compliance check to plan-review verifier template

**type**: claude-md
**target path**: `.claude/CLAUDE.md`
**rationale**: Three-session recurrence on the file:line /
cycle-marker / stale-reference family. The §7 ban was added two
retrospectives ago (ba3ea6e2) but the rule is not enforced at the
plan-review stage. The current session's dual-verifier (checklist
+ adversarial) cleared a 549-line plan that should have been
rewritten before execution — and the docs LANDED commit that
followed added 64 L<n> references across 9 MDs. The fix is not a
new rule (the rule already exists), it's a process step: every
plan-review verifier prompt MUST include an explicit
"CLAUDE.md compliance" check covering at minimum the §6 (no
push, no TaskStop), §7 (no file:line, no cycle markers, no inline
SHA), and §8 (workflow tool vs agent tool routing) rule families.

The existing §8 bullet "Dupla ellenőrzésnél a két verifier kapjon
ELTÉRŐ szöget" already mandates angle diversity but doesn't
specify what angles. Adding "CLAUDE.md compliance" as a
third-angle category fills the gap and would have caught this
session's 64 L<n> violations at the plan-review stage, not at
the code-review stage where remediation is much more expensive.

Proposed addition (insert into §8 next to the dual-verifier
bullet, as a new sub-bullet on the same topic):

```
- **Plan-review verifier prompts MUST include a CLAUDE.md compliance
  check.** Beyond the dual angle split (checklist + adversarial),
  every verifier must explicitly grep the plan/MD text for the
  §6/§7/§8 forbidden patterns: `\bfile:\d+` style line refs,
  `cycle N` / `attempt N` / `phase N` iteration markers, inline
  SHAs outside `(this commit)` placeholders, `git push` /
  `git reset --hard` / `TaskStop` usage. Catching these at the
  PLAN-review stage (before the workflow runs) saves a
  full-codebase docs sweep on `Skipped` findings later. Precedens:
  2026-09-13 3a4147ed G.3 cycle — a 549-line plan cleared
  dual-verifier with 13 PASS + 3 FAIL + 3 CRITICAL + 4 HIGH + 5
  MEDIUM + 5 LOW, none of which flagged the L<n> references that
  ended up in 64 lines across 9 MDs (`docs/refactor-to-classbase/
  g-channel-coordinator/*.md`). The `/code-review max --fix` Skipped
  finding remediation is dual-written to `.claude/shared-memory/
  g3-md-line-refs-deferred.md` for the next session; the rule
  change would have caught it at plan-review time, when the fix
  cost was 1 file instead of 9.
```

### 2. Workflow tool `name` parameter: inline-passed scripts are not registered globally

**type**: memory
**target path**: `.claude/shared-memory/workflow-inline-script-not-registered-by-name.md`
**rationale**: The session hit a Workflow tool error
`"Workflow 'g3-liveness-tracker' not found. Available:
deep-research"` when trying to re-invoke an inline-passed script
by its `meta.name` field. The workflow-authoring skill doc says
inline-passed scripts are persisted to a file under the session
directory but are NOT registered as globally-named workflows.
Re-invocation must use `{scriptPath: "<persisted-path>"}`, not
`{name: "<meta.name>"}`. This is a workflow-authoring gotcha
that costs a turn each time a future session tries to re-run a
workflow by name. Recording it in shared-memory surfaces it via
the agent's semantic search on `Workflow tool gotcha` /
`workflow-authoring name not found` queries.

Proposed content (body of the topic file):

```
# Workflow tool: inline-passed scripts are not registered by name

When the Workflow tool is called with `script` (the inline source)
set, the script is auto-persisted to a file under the session
directory (e.g.
`/Users/eggp/.claude/projects/<project>/<session-id>/workflows/scripts/<meta.name>-<runId>.js`),
but the script is NOT registered as a globally-named workflow.
The only globally-registered name is `deep-research` (and any
other workflow explicitly registered by the user via `/workflows`).

To re-invoke, pass `{scriptPath: "<persisted-path>"}`, NOT
`{name: "<meta.name>"}`. The latter returns:

  <tool_use_error>Workflow "<meta.name>" not found.
  Available: deep-research</tool_use_error>

Symptom: a session passing inline succeeds and persists the
script. A later session (or the same session) trying to re-run
with `{name: "<meta.name>"}` hits the false "not found" error.

Fix: read the persisted file path from the FIRST invocation's
tool result (the result includes the `path` field), and pass it
as `scriptPath` in subsequent calls. Or re-Pass the inline
`script` again (the tool will persist it to a new path).

Precedens: 2026-09-13 3a4147ed G.3 cycle — 3rd Workflow call
in the session used `{name: "g3-liveness-tracker"}` and was
denied with the "not found" error. The first two calls (one with
the full inline script, one empty) succeeded; the workflow ran
end-to-end via the inline script. The 3rd call's failure cost
nothing in this session (the workflow was already running), but
in a future session trying to re-invoke by name it would cost
the discovery turn.
```

Index entry (one-line summary for `.claude/shared-memory/INDEX.md`):

```
- `workflow-inline-script-not-registered-by-name` — Workflow
  tool `{name: ...}` does not find inline-passed scripts; use
  `{scriptPath: ...}` to re-invoke. Cost: 1 false "not found"
  error per session that tries by name.
```
