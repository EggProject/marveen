## Proposals

### 1. Add a cascading-failure warning + parser-error reference to `workflow-authoring`

- **type**: `update-skill`
- **target path**: `packages/shared/.agents/skills/workflow-authoring/SKILL.md` (or the next equivalent plugin-bundled location; the skill is exposed as `workflow-authoring` in Claude Code and may live in a plugin directory if `packages/shared/.agents/skills/` does not contain it here)
- **rationale**: In one session of cast-cleanup work the Workflow tool returned the same `Invalid workflow script: Script parse error — Workflow scripts must be plain JavaScript` ten times across seven workflow scripts. Each parse error triggered an Edit-attempt whose source string had drifted and produced `String to replace not found in file` (3 occurrences). The error message itself points at `workflow-authoring`, so the skill owns the fix. A short "Cascading failure: parse error → Edit → string-not-found" subsection that names the most common tokens (`names, reason}` from a leftover `Record<string,...>`, `Type imports MUST be ABOVE`, `as` casts, `\uXXXX`, `(name in ab)`, `(async () => {...}) as unknown as typeof fetch`, `vi.hoisted` placement) and prescribes the cheapest recovery would let the next author re-author from scratch instead of stacking broken Edits. The lesson is non-obvious (the parser's diagnostic is partially truncated), recurs across cycles, and is broadly reusable for every Workflow tool run in the project.
- **full proposed content**: a new section appended to the existing skill, in the same Markdown style as the rest of the file, roughly:

```markdown
## Cascading failure when a workflow script fails to parse

The Workflow tool parses scripts as plain JavaScript even though the
file extension is `.ts`. When a script fails to parse, do **not** try to
Edit the file in place to remove the offending token: the parser
offsets cited in the error refer to the source as written, and by the
time you run `Edit` against a partially-flowed file the source has
shifted, so the `Edit` replys `String to replace not found in file` and
the round trip is wasted.

Cheapest recovery path:

1. Read the full script back from disk.
2. Re-author it from scratch, this time keeping **zero TypeScript
   syntax** in the script body:
   - no type annotations on parameters or locals
   - no interfaces, no `type X = ...` aliases, no generics
   - no `as` casts, no `as unknown as`, no `satisfies`
   - `import type` is allowed only if every import in that line is a
     type import (otherwise the line is parsed as a value import and
     the names leak into the script namespace)
   - `vi.hoisted` must come **before** any `import type` line that
     the cast-mock pattern uses for hoisting
3. Re-submit the script. If it still fails, do not debug specific line
   ranges; rewrite the script as a small working skeleton (one step
   per `phase:`) and grow it back.

### Most-frequent parser diagnostics in this codebase

These tokens have caused parse failures across recent cycles. Use them
as the first thing to grep for when the parser rejects a script:

- `names, reason}. Each import should be a type import` — leftover
  generic type argument on a Record-style import
- `Type imports MUST be ABOVE the vi.hoisted block` — type import is
  positioned **after** the `vi.hoisted(...)` call
- `\uXXXX` escape sequence errors — backslashes inside template
  literals were passed through `JSON.stringify` twice
- `Single casts -> satisfies or proper typing` — direction-typed
  `as` cast on a value
- `(name in ab) guard prefix` — TypeScript `in`-operator narrowing
  inside a comment-style ternary
- `(async () => {...}) as unknown as typeof fetch` — multi-line
  parenthesized cast of an arrow expression
- `above the beforeEach instead of the globalThis.D` —
  `vi.hoisted` placed below the `beforeEach` instead of at module
  top level

If your script triggers any of these, do not Edit around them;
rewrite the whole script.
```
