# Memory Review

A deliberate, user-driven pass over `.claude/shared-memory/`. It finds entries
that have stopped being trustworthy and asks about each one. It changes nothing
on its own.

## When to run it

Run it when the user asks. `pnpm claude:memory status` answers whether one is
due, and ranks its reasons deliberately:

- **Strong**: the index has reached 80 percent of either cap, 200 lines or
  25600 bytes. The SessionStart hook injects only the index, and silently drops
  everything past that cap, so an overgrown index costs context that no session
  can see it is missing.
- **Medium**: 10 new entries since the last review, or no review has ever run
  and there are 5 or more entries.
- **Weakest, and last on purpose**: 90 days elapsed. Time passing says nothing
  about whether any fact actually moved.

Also run it when a retrospective is about to propose an entry that looks like a
duplicate of, or a contradiction with, one already stored. Review the existing
entry before a second one lands beside it.

With a handful of entries there is usually nothing to find. A run that reports
no findings is a normal, correct outcome. Do not pad it with weak findings to
justify the run.

## The store

`.claude/shared-memory/MEMORY.md` is the index, one line per entry as
`- [<topic>](<topic>.md): <summary>`. Beside it sits one `<topic>.md` per entry:

```
# <topic>
Recorded: YYYY-MM-DD

<body>
```

`pnpm claude:memory` is the only interface: `list`, `search`, `read`, `write`,
`remove`, `status` and `reviewed`, with `--help` for the flags. The heading and
the `Recorded:` line are generated by `write`, so `--content` carries the body
alone. The index preamble carries a `Reviewed: <date> (<N> entries)` line,
written by `reviewed` and read by `status`.

`Recorded:` is a **last-written** date, not a created date. A rewrite resets it.
An entry with no `Recorded:` line predates the field and its true age is
unknown, which is a reason to read it, not a reason to act on it.

## Phase 1: status and inventory, in this session

Always start here:

```bash
mise exec -- pnpm claude:memory status
```

It prints the entry count, the index size against both caps, the last review
date, and a closing `Review due: yes` or `Review due: no` with the reason.
Report that state to the user before scanning anything. When the store is still
too small to hold a contradiction, this is the whole honest answer, and it costs
one command instead of a fan-out.

Then, from the index alone:

```bash
mise exec -- pnpm claude:memory list
```

- group the topics into chunks of at most 4 for phase 2,
- note the pairs whose summaries look like the same subject, as duplicate or
  supersede candidates.

If a summary line links a topic file that does not exist, or a topic file has no
index line, note it: the fix is a rewrite through `write`, not a finding about
the entry's content.

## Phase 2: fan out the mapping, `researcher-sonnet`, `model: sonnet`

Spawn one subagent per chunk, all in one message so they run concurrently. Four
topics per subagent is the ceiling: small enough that a subagent can quote every
claim an entry makes instead of summarizing it away, which is what the later
phases need.

Give each subagent its topic names and ask it to run
`mise exec -- pnpm claude:memory read <topic>` for each, then report per topic:

- the `Recorded:` date, or that the line is absent,
- every concrete claim the entry makes, quoted, with the file path, command,
  table, column, flag, or version each claim names,
- for each of those names, whether it still exists in the repository, with the
  command that showed it. This is the mechanical half of the contradiction
  check and needs no judgment: a path that no longer resolves or a command that
  no longer exists is a candidate, not a verdict.

Send the duplicate and supersede candidate pairs from phase 1 to one more
subagent of the same type, which reads both topic files and reports what the two
entries actually share and where they differ.

## Phase 3: verify the contradictions, `reviewer-opus`, `model: opus`

One subagent per suspected contradiction, again spawned together. Judging
whether an entry genuinely contradicts the current code, or merely describes it
in older words, means reading the real code and weighing intent. That is the
only part of this skill worth opus.

Give each subagent the quoted claim, the topic body, and the evidence phase 2
found, and ask it to refute the claim against the current
`.claude/CLAUDE.md`, `.claude/rules/*.md`, and repository source. A suspicion it
cannot ground in a specific file and line is reported as a suspicion and does
not become a finding.

## What counts as a finding

1. **Contradicts** the current code, `.claude/CLAUDE.md`, or
   `.claude/rules/*.md`. Needs a file and line from phase 3.
2. **Duplicates** or nearly duplicates another entry.
3. **Superseded** by a newer entry on the same subject.
4. **Old, and the facts it rests on have changed.** Both halves are required.
   Age alone is never enough: an architectural decision with its reason can be
   permanently true at four years old, and a one-day-old entry can already be
   wrong. An entry is a finding because a specific fact under it moved, and the
   date is only the hint that sent someone looking.

## Phase 4: present and ask

Report every finding with its evidence before asking about any of them, so the
user sees the whole picture first:

```
<topic>  |  <category>  |  recorded <date>
Claim:    "<the quoted line from the entry>"
Evidence: <file:line, command output, or the other topic it duplicates>
Proposed: <keep | supersede | merge | delete>, with the exact replacement body
```

Then one AskUserQuestion per finding, in that order. The options map to what
phase 5 will run:

- **Keep**: nothing runs.
- **Supersede**: `write` the topic with the corrected body.
- **Merge**: `write` the surviving topic, `remove` the other.
- **Delete**: `remove` the topic.

Show the exact replacement body inside the question. Approval has to cover the
text that will be written, not just the verdict.

A supersede body ends with this line:

```
Superseded YYYY-MM-DD: the entry previously said <X>; that stopped being true because <Y>.
```

## Phase 5: apply

Only for findings the user approved, and only through the CLI:

```bash
mise exec -- pnpm claude:memory write <topic> --summary "<one line>" --content "<body>"
mise exec -- pnpm claude:memory remove <topic>
```

`write` refuses rather than produce an index past the hook's cap, and keeps the
index and the topic files in step. Hand-editing either one skips both checks.

Report what was applied and what was left alone.

## Phase 6: stamp the review

```bash
mise exec -- pnpm claude:memory reviewed
```

This writes `Reviewed: <today> (<N> entries)` into the `MEMORY.md` preamble, and
it is what `status` reads to decide the next review is not yet due.

Run it only when a review actually finished, meaning the user was walked through
every finding and answered each one. A run that found nothing is finished too,
and gets the stamp: that the store was checked and was clean is exactly what the
next reminder needs to know.

**Do not stamp a review the user abandoned part way.** The stamp is what
silences the next reminder, so a false one buys nothing and costs the review
that reminder would have prompted. An abandoned run leaves the store as it was,
still due, and says so in its closing report.

Never commit: the stamp and any applied change belong to the invoking session's
commit.

## Never

- **Never delete or rewrite anything without per-item approval** through
  AskUserQuestion. This store is committed history, and a wrong deletion is
  invisible afterwards: nothing in a later session will say the fact used to be
  known.
- **Never offer a bulk "accept all" shortcut.** Per-item confirmation is exactly
  what keeps approval fatigue from turning the review into rubber-stamping,
  which is the documented failure mode of human-in-the-loop gates once the
  volume rises.
- **Never run on a schedule, or automatically after a retrospective.** Rare and
  deliberate is what keeps each review attentive. Surfacing that `status` says a
  review is due is a reminder, and reminders are fine; starting one without the
  user is not.
- **Never use "this entry was never read" as a signal.** The CLI logs no reads
  and no searches anywhere, so that data does not exist. Using it would mean
  inventing evidence.
- **Never delete an entry that merely went out of date.** That is a supersede:
  the topic keeps its name, gets the correct content, and carries the
  `Superseded` line so the next reader can see what changed and why. Deletion is
  for an entry that was never true, or that is no longer about anything.
